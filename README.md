## How to run

The program reads the source code (rules + optional state) from **standard input** and writes the result to **standard output**.

### On Windows (Command Prompt)

```cmd
python main.py < input.txt
```

### On MyCompiler

1. Open https://www.mycompiler.io/new/python
2. Paste the contents of `main.py` into the editor.
3. Open the **STDIN** panel and paste the program (rules + state).
4. Click **Run**.

### Input format

The program and the initial state are separated by the literal line `State:`. If no state is provided, the `State:` separator may be omitted.

Example:

```
rule r1:
if temp > 30 then alert
rule r2:
if alert then fan_on

State:
temp = 35
```

- Rules follow the grammar described below.
- The state contains either variable assignments (`id = integer`) or active facts (`id`), one per line.
- Blank lines and extra whitespace are ignored.

### Output format

1. The set of facts **derived during execution** (i.e., facts produced by rule firing — initial facts are not echoed), sorted lexicographically, one per line. If no facts are derived, the program prints `(no output)`.
2. Static-analysis messages (conflicts, redundancies, potentially inactive rules), one per line.

## Grammar

The original grammar in the assignment is not LL(1) because the production

```
Cond → Cond AND Cond | Atom
```

is left-recursive and ambiguous. We transformed it into the following equivalent LL(1) grammar (right-recursive, unambiguous, left-associative when built iteratively):

```
Program  → RuleList
RuleList → Rule RuleList | ε
Rule     → rule id : if Cond then id
Cond     → Atom CondTail
CondTail → AND Atom CondTail | ε
Atom     → id AtomTail
AtomTail → RelOp value | ε
RelOp    → > | < | =
```

The parser (`_P` in `main.py`) is a hand-written recursive-descent parser that follows this grammar directly. `Cond` is built left-associatively using a `while` loop so that `a AND b AND c` is parsed as `And(And(a, b), c)`.

## AST

The AST is represented with Python tuples that match the canonical structure required by the assignment:

```
('Program', [rules])
('Rule', name, condition, ('Action', id))
('And', left, right)
('Cmp', id, op, value)        # op ∈ {'>', '<', '='}
('Fact', id)
```

## Evaluation

Evaluation follows the fixed-point semantics described in the assignment:

1. Initialize the active facts with the initial facts.
2. Repeatedly scan all rules; whenever a rule's condition is true, add its action to the active facts.
3. Stop when an iteration adds no new facts.

The result is independent of rule order.

## Static analysis

After execution, the analyzer reports:

- **Conflict** — two or more rules produce the same action under *different* conditions:
  `Action <id> generated by r1, r2, ...`
- **Redundancy** — two or more rules have *identical* conditions and the same action:
  `Redundant rules: r1, r2`
- **Potentially inactive rule** — a rule whose condition cannot be made true (variables are immutable, and no required fact is initially active or produced by any rule) and whose action is not consumed by any other rule. Rules already flagged as conflict/redundant are not reported as inactive.
